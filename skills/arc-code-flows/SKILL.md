# Arc Code Flows

Arc Code (`arc-code-cli` on npm, run as `npx arc-code generate-diagrams`)
is a separate static-analysis CLI. It reads TypeScript/JavaScript source
with the TS Compiler API -- no AI, no network, no code execution -- and
writes Mermaid diagrams to `.arch/` describing the architecture that
actually exists *in that one project*. This skill is the Claude Code side:
how to *consume* that output instead of re-deriving the same facts by
re-reading source every time, and how to stage a proposed change for
review before touching code.

**This skill carries no knowledge of any particular project's domain.**
Every route path, class name, function name, and module path below is a
placeholder for illustration only. The real names always come from
`.arch/manifest.json` itself, generated fresh for whatever project it was
run against -- an e-commerce API, a CLI tool, a game, anything. Never
assume a project has a "customer," "user," "order," or any other
particular resource just because an earlier project you saw did; read the
actual `index` and `resources` fields every time.

## `.arch/` is the source of truth

The real `.arch/` diagrams (the root-level files and everything under
`domains/`) are the authoritative description of this project's current
flows, structure, and dependencies -- not Claude's own inference from
skimming some of the code, not general assumptions about "how this kind of
app usually works." When `.arch/` describes something and isn't stale,
defer to it over a guess, even a well-informed one.

This authority has two explicit limits, both already covered below: it's
*current-state* truth only, bounded by `manifest.json`'s `generatedAt` (step
4 of the next section handles staleness); and it does not extend to
`.arch/.temp/` -- a pending proposal is a draft under review, not yet a
fact about the codebase, until the user approves and it's actually
implemented.

## Reading an existing flow (cheaper than re-reading source)

1. Read `.arch/manifest.json`. Its `index` field maps exact names
   *specific to this project* to file paths. The shape is always the same
   five categories; the keys inside them are whatever this project's own
   routes/functions/classes/modules happen to be called:
   ```json
   "index": {
     "routes": { "<METHOD> <path>": "routes/<n>_<slug>.mmd" },
     "sequence": { "<METHOD> <path>": "sequence/<n>_<slug>.mmd" },
     "functions": { "<ClassName>.<method>": "functions/<ClassName>_<method>.mmd" },
     "classes": { "<ClassName>": "classes/<ClassName>.mmd" },
     "dependencies": { "<module/path>": "dependencies/<slug>.mmd" }
   }
   ```
2. Look up the thing being asked about by its exact name as it appears in
   *this project's* index (route as `"METHOD /path"`, function/method as
   `"ClassName.method"`, class by name, module by its path without
   extension). Read *only* that one `.mmd` file under
   `.arch/<path-from-index>` -- not the combined root-level
   `routes.mmd`/`functions.mmd`/etc. unless a project-wide view is
   actually what's needed.
3. If a resource-scoped view is more relevant (the question is about one
   feature end-to-end), check `manifest.json`'s `resources` list -- it
   enumerates whatever resources *this* project actually has (could be
   zero, could be a dozen, under any names) -- for a matching entry and
   read its `dir`'s `architecture.mmd`/`routes.mmd`/`sequence.mmd`/
   `classes.mmd`/`dependencies.mmd`/`functions.mmd` instead of the
   mini-flows.
4. If the exact name isn't in the index (new code written after the last
   `.arch/` generation, or a project that's never run arc-code), fall back
   to reading source normally. **Never present a diagram's contents as
   current if it might be stale** -- `.arch/` reflects whatever the source
   looked like at `manifest.json`'s `generatedAt`, nothing newer. If source
   has visibly changed since (recent edits this session, a stale-looking
   diff), say so and offer to regenerate: `npx arc-code generate-diagrams`
   run from the project root (ask before running it unprompted, same as any
   other command with side effects -- it only writes under `.arch/`, but
   it's still an action, not a read).
5. The six diagram kinds and what each is good for (same six file names
   in every project, root-level and per-resource alike):
   - `architecture.mmd` -- detected layers (or the real directory graph)
   - `routes.mmd` -- HTTP routes as a flowchart (request -> handler -> calls -> return)
   - `sequence.mmd` -- the same routes as a sequenceDiagram (who calls whom, in order)
   - `classes.mmd` -- classes/interfaces with members and extends/implements/uses relations
   - `dependencies.mmd` -- the import graph, with cycles and layer violations flagged
   - `functions.mmd` -- every function/method with heuristic Big-O complexity and a call graph
6. **If the project has a frontend** -- check `manifest.json`'s `frontend`
   field first (`{ "analyzed": "react" | null, "detected": [...] }`).
   When `analyzed` is `"react"`, two more root-only files exist (no index
   entry, no per-resource scoping yet -- read them directly, same as
   `architecture.mmd`):
   - `components.mmd` -- every React/Next.js function component, its
     props/hooks, and `--> : renders` edges to other known components.
     Colored Page vs. Component.
   - `pages.mmd` -- UI routes (Next.js file-based routing, React Router's
     JSX `<Route>` form), same flowchart shape as `routes.mmd` but
     `method: "PAGE"` instead of an HTTP verb.
   When `detected` lists a framework `analyzed` doesn't name (e.g. Vue,
   Angular, Svelte), say so plainly instead of pretending there's a
   diagram for it -- there isn't yet, only React/Next.js is structurally
   analyzed as of this version. Fall back to reading source for anything
   in an unanalyzed frontend framework.

## Showing what changed architecturally (diff-diagrams)

When the question is about *change* rather than current state -- "what
changed since the last commit," "diagram what this branch changes,"
"compare main and this PR architecturally" -- don't diff `.mmd` text and
don't infer structure from `git diff` yourself. Run:

```bash
npx arc-code-cli diff-diagrams --from <ref> [--to <ref>] [--out <dir>]
```

`--from` is the "before" point (a branch, tag, or commit); `--to` defaults
to the working tree as it sits on disk, so the default comparison is
"what have I changed since `<ref>`" -- pass another ref to compare two
commits/branches directly instead. This writes the same 6 root diagrams
again (`architecture.mmd`, `routes.mmd`, `sequence.mmd`, `classes.mmd`,
`dependencies.mmd`, `functions.mmd`) to `--out` (default
`.arch/.diff/<from>..<to>/`), color-coded:

- 🟩 green -- added  ·  🟨 yellow -- modified  ·  🟥 red -- removed  ·  🟦 blue -- unchanged

Classification is structural (same analyzer Arc Code always uses, run
against both snapshots and diffed by route/class/function/module key), not
by filename or line-diff -- a renamed file that changed nothing it exports
shows "unchanged," and a method whose body changed but whose
signature/calls didn't is also "unchanged." Read the resulting files the
same way as any other `.arch/` diagram (per "Reading an existing flow"
above) and describe what's colored what -- this command is read-only
(writes only under `.arch/.diff/`), so no approval step is needed before
running it, unlike `generate-diagrams` or implementing a change.

## Draw before you build

This is the core reason this skill exists, not an optional extra: when a
task adds, removes, or moves anything `.arch/` would represent -- a route,
a function or method, a class, or a dependency between modules -- draw the
proposed result as Mermaid diagrams, in the exact same format as `.arch/`
itself, *before* writing or editing a single source file. The user reviews
the shape of the change as a diagram, not as a diff of code that doesn't
exist yet. Only a genuinely trivial edit (fixing a typo, a comment, a
one-line bug fix that doesn't add/remove/move a route, function, class, or
dependency) skips this -- when in doubt, draw it; a small proposal costs
little and a skipped one costs a user reviewing a surprise.

This mirrors Arc Code's own intended workflow end to end: a user's request
becomes an AI-proposed architecture change, which gets drawn and validated
as diagrams, then a human approves it, *then* the AI implements it, and
Arc Code can later verify the real code matches what was approved. This
skill is the "propose and draw" half of that loop running inside Claude
Code; regenerating `.arch/` after implementing is the "verify" half.

**Never hand-write the `.mmd` files.** Mermaid has real, non-obvious
reserved-character and escaping rules that differ *by diagram type*
(`classDiagram` reserves `< > { } | :`; `sequenceDiagram` breaks if you
HTML-escape the very characters `flowchart` requires escaping) -- rules
discovered the hard way while building Arc Code itself, not guesswork.
Describe the proposal as data instead, in the JSON shape Arc Code defines
for exactly this (`schema/proposal.schema.json` in the `arc-code-cli`
package). Seven tags, each independently optional -- include only what
changes:

- `architecture`, `classes`, `interfaces`, `dependencies`, `functions` --
  same shape as the real diagrams.
- `routes` and `sequence` -- independent of each other even though both
  describe HTTP routes (same entry shape for both): ask for the flowchart,
  the sequence diagram, or both, by including one or both keys.
- `domains` -- a map of resource name to the same 6 tags above, scoped to
  it, mirroring `.arch/domains/<resource>/`. Use this when the proposal is
  (or belongs to) a specific resource, not a project-wide change.

`arc-code-cli` (or the MCP tool below) reuses Arc Code's own renderers, so
the output is guaranteed the same valid Mermaid `.arch/` itself uses.

**No `components`/`pages` tag exists yet** -- a proposed new React
component or page can't be rendered this way today, only the 6 backend-
shaped tags above. For a frontend change, describe the proposed
component/page in plain language (what it renders, its props) instead of
drawing it, and say plainly that this is a gap, not a silent skip.

Concretely, in this exact order:

1. Shape the proposal as a JSON object conforming to
   `schema/proposal.schema.json`, including only the tags that change.
2. Render it, by whichever of these two is actually available:
   - **If an MCP server named `arc-code` (or similar, check the project's
     `.mcp.json`) is connected**, call its `render_proposal` tool directly
     with that JSON as arguments, plus `projectDir` set to the project's
     absolute root path. No file, no shell command.
   - **Otherwise**, write the JSON to a temp file (anywhere -- it's an
     intermediate input, not a deliverable) and run
     `npx arc-code-cli render-proposal <that-file.json>`.
   Either path writes to a fresh `.arch/.temp/<uuid>/` folder in the
   project -- a new UUID per request, not a fixed shared name -- so one
   proposal never collides with or overwrites another still pending
   review. Both the MCP tool's response text and the CLI's stdout report
   the exact path written to; read it from there rather than guessing it.
   Only the sections the JSON actually included get rendered, matching
   "write only what would change."
3. **List every file written to that `.arch/.temp/<uuid>/` folder and what
   each one shows** (one line per file is enough, e.g. "`routes.mmd` --
   the new `POST /refunds` route and its call chain"), and name which real
   `.arch/` file each corresponds to, so the user can compare before
   deciding.
4. **Explicitly ask for approval** ("does this look right to implement?"
   or equivalent) and wait for a yes. A proposal sitting in
   `.arch/.temp/<uuid>/` is not itself approval, and moving on to
   implementation without asking defeats the entire point of drawing it
   first.
5. Do not touch real source files until the user approves.
6. After approval and implementation, regenerate the real `.arch/` (ask
   before running `npx arc-code generate-diagrams`) and delete that one
   `.arch/.temp/<uuid>/` folder -- it was scratch space for this review,
   not a permanent part of `.arch/`. Leave any other `<uuid>/` folders
   under `.arch/.temp/` alone; they belong to other proposals still
   pending their own review.

## What this skill does not do

- It does not assume anything about the target project -- no particular
  domain, resource names, or file layout. Every example above is a
  placeholder; the real content always comes from that project's own
  `.arch/manifest.json`.
- It does not run `arc-code-cli` as a silent side effect of a hook --
  every invocation is an explicit step this skill itself just told Claude
  to take, with the user able to see it happen like any other command.
  That said, the two commands carry different weight: `generate-diagrams`
  overwrites the real `.arch/` (the source of truth) and should still get
  the user's go-ahead before running, same as any other write to tracked
  project files; `render-proposal` only ever writes to a fresh, disposable
  `.arch/.temp/<uuid>/` folder, so running it to draw a proposal needs no
  separate permission beyond what this skill already describes.
- It does not validate that a proposal is architecturally sound -- that's
  still the user's call, and (per Arc Code's own design) a future automated
  "does the code match the approved diagram" check, not something this
  skill fabricates today.
